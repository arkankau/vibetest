The issue is in the condition on line 469-472. When `prev_field` is a relation and the current `field` is in `prev_field.path_infos[-1].target_fields`, the part is skipped (not added to relation_parts). This is meant to handle concrete inheritance where following a parent link and then accessing the parent's pk is the same as accessing the child's pk. But it incorrectly treats a OneToOneField used as a primary key (like `Restaurant.place`) the same way.

When processing `restaurant__place__country`:
1. `restaurant` - field is ForeignKey to Restaurant, added to relation_parts


2. `place` - prev_field is restaurant (FK to Restaurant), target_fields would be Restaurant's pk which IS `place` (since place is the primary key). So `field` (place) IS in target_fields, so it's skipped.
3. `country` - added to relation_parts

Result: relation_parts = ['restaurant', 'country'], which becomes 'restaurant__country' - not in list_filter. The fix needs to distinguish between skipping a true primary key field versus skipping a relation field that happens to be a primary key, so the optimization only applies when we're resolving a pk locally rather than traversing another relation.
